# Project Management System (PMS) Mobile App Implementation Plan

## Goal Description
Build a production-grade, enterprise-ready Project Management System mobile application using Flutter. The app will strictly follow the provided API backend documentation (`backend/API_HUB.md`) as the single source of truth and adopt the design system specified in `karan_pms_application/DESIGN.md`. The initial scope will focus solely on 4 core modules: Authentication, Home Dashboard, Projects, and Tasks.

> [!NOTE]
> Since the `karan_pms_application` was just initialized with `flutter create .`, there is no "existing architecture" or "existing state management" yet. The proposed architecture will establish a robust, feature-based clean architecture to support an enterprise-grade application.

## User Review Required

> [!IMPORTANT]  
> **State Management & Routing**: Since the project is brand new, I propose using **Riverpod** (`flutter_riverpod`) for state management due to its safety and scalability, **GoRouter** for declarative routing, and **Dio** for advanced networking (interceptors for token refresh). Please confirm if these packages are acceptable.

> [!IMPORTANT]  
> **Secure Storage**: For storing the `accessToken` and handling the `refreshToken` (if we need to store it locally, though API_HUB says refresh token is an httpOnly cookie, which implies the mobile app might need a cookie jar or to handle the refresh token via a response body if the backend was adjusted for mobile, or we simply use `dio_cookie_manager`). I will configure a Cookie Manager for Dio to handle the httpOnly refresh token cookie automatically. Please confirm this approach.

## Proposed Architecture

The application will be structured using a **Feature-Based Clean Architecture**:
- `lib/core/`: Application-wide core configurations.
  - `network/`: Dio client setup, interceptors (Auth, Error, Retry).
  - `theme/`: Design tokens mapped from `DESIGN.md` (Colors, Typography, Spacing).
  - `router/`: GoRouter configuration and route definitions.
  - `storage/`: Secure token storage and preferences.
- `lib/shared/`: Highly reusable UI components (Buttons, Cards, Inputs, Skeletons, Empty States).
- `lib/features/`: Feature-specific logic containing its own models, repositories, providers/controllers, and UI.
  - `auth/`: Login, Session Management.
  - `dashboard/`: Overview Cards, Recent Projects, My Tasks.
  - `projects/`: Listing, Project Details, Project Cards.
  - `tasks/`: Listing, Task Details, Task Creation, Task Cards.

## Verification Plan

### Automated Tests
- No automated tests requested in the prompt, but the app will be built completely free of lint errors (`flutter analyze`) and strict null-safety checks.

### Manual Verification
- **Auth Flow**: Start app -> Login -> Dashboard -> Restart app -> Auto-login via stored token.
- **Token Expiration**: Simulate token expiry and verify the Dio interceptor transparently refreshes using the httpOnly cookie and retries the failed request.
- **UI Responsiveness**: Verify layouts on simulated Small Phone and Tablet screens without overflow errors.
- **Design System Fidelity**: Compare padding, fonts, and colors to the tokens described in `DESIGN.md`. All loaders should be premium skeletons, avoiding `CircularProgressIndicator`.
